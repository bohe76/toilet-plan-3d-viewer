# 도면 8장을 AI와 함께 3D 화장실 뷰어로 만든 이야기

이 문서는 개발을 모르는 지인을 위한 글이다. 목적은 두 가지다.

1. 이 프로젝트를 어떤 순서로, 어떤 대화로 만들었는지 이해시킨다.
2. 나중에 비슷한 일을 할 때 그대로 따라 할 수 있는 요령을 남긴다.

글에 나오는 두 주체는 아래와 같다.

- **보헤님**: 프로젝트를 시킨 사람. 대화에서 코드를 직접 쓰지 않았다. 모든 요청이 일상 문장이었다.
- **AI**: Claude Code. 보헤님의 말을 받아 조사하고, 만들고, 검사하고, 보고했다.

근거는 대화 기록 5회분, 작업 저장 기록 60개, 프로젝트 안의 인수인계·검수 문서다.

## 2. 결과물은 무엇인가

- 화장실 8곳(강의동 2·3·4층, 연구동 1·2·3·4·5층)을 위쪽 탭으로 골라 본다.
- 마우스로 돌리고, 확대하고, 안으로 걸어 들어간 시점(눈높이)으로도 본다.
- 두 가지 화면이 있다.
  - **도면 모드**: 원래 스캔 도면 위에 3D 모형을 겹쳐 놓고 맞는지 본다.
  - **실사 모드**: 타일, 도기, 거울, 그림자를 넣어 실제 사진처럼 본다.
- 품목을 누르면 이름, 크기, 도면에 적힌 값인지 AI가 짐작한 값인지가 나온다.

## 5. 시간순 진행

시각은 한국 시간이다.

### 1장. 제안부터 시켰다 (11-21 새벽 01:48)

**보헤님의 첫 요청**

> 폴더에 pdf가 있어. 평면도인데 총 8장이야. 이걸 3D 화면으로 8개의 탭으로 만들어서 각각을 보고 싶어. 어떤 스택을 쓰고 어떤 기능을 넣을지, 화면 배치와 마우스로 어떤 동작을 할지 제안해.

"만들어라"가 아니라 **"제안해라"**로 시작했다. 이것이 이 프로젝트의 첫 번째 요령이다.

**AI가 한 일**

1. PDF를 열어 확인했다. 8장 모두 A3 가로 도면이고, 글자와 선을 읽을 수 없는 스캔본임을 알아냈다.
2. 3D로 만드는 방법을 3가지로 비교했다.
   - A. 도면 그림을 바닥에 깔고 기울여 보기. 가장 쉽지만 벽이 서지 않는다.
   - B. 치수를 읽어 벽·변기를 직접 모형으로 만들기. 입체감이 나지만 숫자를 전부 읽어 옮겨야 한다.
   - C. B를 만들고 그 아래 원본 도면을 깔기. 모형이 틀리면 바닥 도면과 어긋나서 눈으로 바로 보인다.
3. C를 추천한 이유를 "검증이 쉽다"로 설명했다.
4. 화면 배치, 마우스 동작, 정확도의 한계를 표와 그림으로 보였다.
5. 마지막에 보헤님이 정할 4가지를 물었다.

**보헤님의 답 (번호로 한꺼번에)**

> 1. C. 2. 아니다. 3. 오케이. 4. 점검해. 4번부터 하자. 그리고 반드시 독립 검증 에이전트로 만든 후 실제 도면과 같은지 검수해라.

| 번호 | AI의 질문 | 보헤님의 뜻 |
|---|---|---|
| 1 | 3D 방식은 A, B, C 중 무엇인가 | C |
| 2 | 도면의 손글씨 「조명」 위치 검토가 주목적인가 | 아니다 |
| 3 | 8장 중 1장(가장 작은 것)을 먼저 만들어 확인받는 순서로 할까 | 오케이 |
| 4 | 도구 설정에 문제가 있어 보이니 점검할까 | 점검해라 |

**마지막 문장이 가장 중요했다.** 만든 AI가 스스로 "맞다"고 하지 못하게, 다른 일꾼이 원본과 대조하도록 **처음에** 못박았다. 이 규칙은 끝까지 지켜졌다.

### 2장. 1장짜리 시험작(파일럿)을 만들었다 (11-21 새벽 ~ 05시)

연구동 3층을 첫 시험작으로 골랐다. 가장 작고 단순해서다.

**AI가 한 일**

- 스캔이 0.6~0.8도 기울어 있어서 바로잡았다(보정 뒤 오차 0.065도 이하).
- 눈금자가 들어간 확대 조각 이미지를 만들어 치수 숫자를 **눈으로 읽었다.** 스캔본이라 자동으로 읽을 방법이 없었다.
- 치수 숫자를 모형 데이터(품목 44개)로 옮기고, 3D 화면(탭, 레이어 켜고 끄기, 벽 높이 자르기, 정보창)을 만들었다.
- 별도의 독립 검증 일꾼이 **3번** 검수했다. 1차에서 14곳, 2차에서 3곳, 3차에서 0곳이 나와 통과했다.

**사고: 저장이 18번 연속 막혔다**

AI 도구의 보조 장치가 컴퓨터가 바쁠 때 시간 초과로 모든 저장을 거부했다. 만든 파일 11개가 AI의 임시 기억에만 있는 위험한 상태가 됐다.

- 작업 중간에 보헤님이 짧게 지시한 것들이 있었다.
  > 훅(보조 장치) 시간 늘려라.
  > 아, git 초기화하고, 필요한 문서는 docs 폴더 안에 네가 구조화해서 폴더 만들고 필요한 문서를 작성해라.
  > 지금까지 한 거 저장하고, 커밋 후 세션 종료해서 훅 설정 변경된 걸로 다시 작업하자. 다음 세션에 문제 없게 모든 걸 문서화 해.
- AI는 숨기지 않고 상황을 보고했다. 무엇이 저장됐고 무엇이 안 됐는지 구분해서 적었고, 보헤님이 고를 선택지 2개를 줬다.
- 보헤님은 대화를 종료한 뒤 이어받기(resume)로 다시 열었다. AI는 대화에 남은 내용으로 파일을 다시 썼다.
- 이후 보조 장치의 제한 시간을 5초에서 20초로 늘렸다.

**교훈**: 도구가 막힐 때는 AI가 "지금 무엇이 위험한지"를 먼저 말하게 한다. 보헤님은 선택만 하면 된다.

**보헤님의 확인과 새 요구 (11-21 새벽 05시)**

화면을 본 보헤님이 5가지를 더했다.

> 1. 셰이더(3절 참고)도 넣어서 실사처럼 보이게 하자. top 건축사무소에서 만든 퀄리티 정도가 되어야 한다.
> 2. 도면에 없어도 상식적으로 있어야 하는 거면 있어야 한다. X는 물이 빠지는 방향이다. 높이는 없다. 네가 생각하는 상식적인 높이로 해라.
> 3. 착수하지 마라(나머지 7개 탭).
> 4. 알겠다.
> 5. 상하좌우 이동이 되는 기능이 있으면 좋겠다. 마우스 우측으로 해도 되고, 키보드 화살표도 되고. **이해가면 설명.**

AI는 바로 만들지 않았다. **자기가 이해한 내용을 항목별로 풀어서 설명**하고 "맞으면 진행"을 요청했다. 특히 AI가 **짐작한 것 2가지**를 따로 표시해 확인을 받았다(X 표시 칸의 중앙에 배수구를 넣는다, 위생기구 모양은 외부 모델 없이 직접 만든다).

보헤님은 "추정 맞다. 색상은 호텔 화장실 느낌으로 가자"고 답했다. 그리고 문서화한 뒤 세션을 끝냈다.

**교훈**: "이해가면 설명"이라는 한마디가 AI의 오해를 구현 전에 걸러낸다. 보헤님은 새 기능을 제안받거나 큰 요구를 줄 때 이 문구를 거듭 붙였다.

### 3장. 실사 모드와 고품질 렌더 (11-21 05시 ~ 14시)

"업무준비"라고 한마디 입력하면 AI가 전날 인수인계 문서를 읽고 오늘 할 일 목록을 만든다. 이 습관은 매 세션 반복됐다.

**AI가 한 일**

- 재질(타일, 도기, 금속, 거울), 조명, 그림자를 넣은 실사 모드를 만들었다.
- 빛을 정밀 계산하는 고품질 렌더를 만들었다. 켜고 끄는 스위치다.
- 도면에 없지만 있어야 할 품목(세면대 상판, 천장, 조명, 휴지걸이 등)을 "가정" 표시를 달아 넣었다. 도면 근거 품목과 섞이지 않게 구분했다.

**보헤님의 피드백과 AI의 반응**

| 보헤님의 말 | 일어난 일 |
|---|---|
| 「내 컴퓨터가 지금 내장 그래픽뿐이다. 참고해」 → 곧이어 「내 컴퓨터를 기준으로 하지 마라. 사양이 낮으니」 | AI가 품질을 낮춰 맞췄다가 정정받았다. 품질은 일반 PC 기준으로 잡고, 이 PC에서는 멈추지 않게만 하는 규칙이 생겼다 |
| 「고품질에서 상단이 막혀 있으니 안을 볼 수 없잖아. 상단 없애자」 | 위에서 내려다볼 때 천장이 가리지 않게 숨기도록 했다 |
| 「천장에 달리는 것이 있다면 실내에서 천장 구현해야 할 것 같은데」 | 조명과 환기구가 천장에 달린다는 점을 짚은 것이다. 결국 **실내에서 볼 때만 천장을 그리고, 위에서 내려다보면 숨기는 방식**으로 정해졌다. 조명과 환기구는 천장이 없어도 제자리에 둔다. 이 과정에서 천장은 "위만 숨김 → 완전 제거 → 실내에서만 그림"으로 세 번 바뀌었다 |
| 「판독 메모는 페이지에 필요 없다」 | 정보창에서 AI의 읽기 메모를 뺐다 |
| 「기본은 고품질 렌더를 켜는 걸로」 → 「고품질 렌더는 on/off로 하자」 → 「실사에서 고품질 렌더는 꺼짐을 기본으로」 | 기본 켜짐 → 켜고 끄는 스위치 → 기본 꺼짐 순서로 바뀌었다. AI는 그때마다 바로 반영했다 |
| 「고품질 렌더에서 미리 평균값으로 그리면 안 되나?」 → 「A + B로 하자」 | AI가 고른 방법 2개를 합쳤다. 처음엔 일반 화면을 보여 주고, 표본이 모이면 잡티 제거 필터를 거쳐 바꾼다 |

한 번은 보헤님이 영문 입력 상태에서 한글을 쳐서 글자가 깨졌다(「rlrlqhsdms rhvnawlf…」). AI는 이를 한글 자판으로 되돌려 **"기본은 고품질 렌더를 켜는 걸로 하자"**로 읽었다. 읽은 결과를 대화에 적어 두어서 틀렸으면 바로잡을 수 있었다.

**첫 공개 배포 (11-21 14:26 지시)**

> 공개 원격 레포 적당하게 이름 만들어서. pdf는 제외하고, 우리 문서도 제외하고, 결과물만 볼 수 있게 올리자.

이어서 "공개 저장소는 URL로 볼 수 있는 주소를 받을 수 있잖아. 그 주소에서 정상적으로 보이게 하면 된다"고 **완료 기준**을 한 문장으로 알려 줬다.

AI는 공개용 저장소(인터넷 보관함)를 따로 만들고 **완성된 화면 파일만** 올렸다. 원본 PDF와 작업 문서는 올리지 않았다. 공개 기록에 개인 메일이 남지 않도록 GitHub의 가림 주소(noreply)를 작성자로 썼다.

### 4장. 마무리 손질, 그리고 7개 탭 착수 승인 (11-21 15시 ~ 18시)

- 보헤님이 실사 화면, 색상, 천장 처리를 보고 **"다 좋다. 세션 종료하고, 다음 라운드에 7개 탭 구현하자"**고 했다. 이때 "착수하지 마라"가 풀렸다.

### 5장. 7개 탭을 병렬로 만들었다 (11-21 18시 ~ 11-22 11시)

가장 큰 구간이다. 약 17시간이 걸렸다.

**시작 (11-21 18:17)**

보헤님은 "탭 구현 7개 하기 전에 **대기**"를 명시했다. AI가 문서를 읽고 환경을 점검한 뒤 보고하자, 보헤님이 문서 불일치를 정리시켰고 이어서 물었다.

> 7개 탭을 가장 빠르게 병렬로 구현하는 방법을 제안해.

AI는 코드와 컴퓨터 상태를 확인한 뒤 **7개를 한 번에 띄우지 않는 안**을 추천했다. 이유는 4가지였다.

1. 변기, 세면기 같은 부품 코드가 시험작 파일에 묻혀 있어서, 지금 나누면 일꾼 7명이 부품을 각자 복사한다(탭마다 변기 모양이 달라진다).
2. 컴퓨터 여유(CPU)가 없어서 일꾼 수만큼 느려지고 오류가 는다.
3. 화면 확인 통로가 1개라서 서로 사진을 덮어쓴다.
4. 도면이 3계열(강의동, 연구동 1~2층, 연구동 4~5층)이라 계열 대표가 통과하면 나머지의 본보기가 된다.

그래서 **0단계 공통 준비 → 계열 대표 3개 → 나머지 4개 → 통합** 순서를 제안했다. 보헤님의 답은 "**제안대로 해라.**"였다.

**진행 방식**

- 부품을 공용 파일로 뽑아 7명이 같은 변기를 쓰게 했다. 뽑기 전후에 시험작의 품목 95개가 똑같은지 비교했다.
- 일꾼마다 자기 도면 파일만 고치게 했다.
- 검증 일꾼에게는 **작성자의 결론, 이전 검수 기록, 작성자의 스크립트를 보여 주지 않고** 원본 도면 이미지와 결과 데이터, 화면 사진만 줬다. 이 점이 독립 검증의 핵심이다.
- 일꾼이 끝나도 "끝났다"는 알림이 안 오는 일이 잦았다. 보헤님이 이렇게 지시했다.
  > 이게 이벤트가 안 오는 경우가 자주 있다. 10분마다 idle(쉬는 상태)인 것이 있는지 감시해서 체크하고 필요한 조치를 해라.

  AI가 10분마다 자동 점검을 걸었고, 나중에 보헤님이 "점검 시간을 15분으로 변경하자"고 바꿨다. 점검 때마다 쉬는 일꾼의 보고를 확인하고, 끝난 일꾼은 종료하고, 다음 일을 보냈다.
- 보헤님도 화면에서 쉬는 일꾼을 보고 "끝났다면 죽이고(종료하고), 다른 일 해라"고 지시했다.

**검수에서 나온 것**

- 모든 탭에서 모든 차수에 **"높음(심각)" 등급 불일치는 0건**이었다. 대부분 문짝 끝점 몇 mm 차이 같은 사소한 것이었다.
- 탭마다 검수는 2~7번 돌렸다. 연구동 1층이 7번으로 가장 많았다. 전체로는 약 30번이다.
- 연구동 5층의 남은 오차 3건은 고치지 않았다. 원인이 AI의 판독 오류가 아니라 **스캔 종이 자체의 휨**이었기 때문이다. 왜 그렇게 판단했는지를 검수 기록에 적었다.
- 연구동 2층 점검구(작은 문)는 AI 본체가 직접 도면을 다시 읽고 고쳤다. 자기 판독이라 **독립 검수를 한 번 더** 돌렸다.

**사고: 프로세스 종료 실수**

보헤님이 "고아 프로세스(주인 잃은 프로그램) 죽여라"라고 했다. 보헤님은 AI가 직전에 보고한 1개를 가리킨 것으로 보인다. AI는 범위를 넓게 읽어서 **다른 프로젝트의 로그 감시 프로그램과 잔여 프로그램까지** 여러 개 종료했다. 보헤님의 컴퓨터에는 이 프로젝트 말고도 다른 프로젝트가 돌고 있었다. AI는 그중 두 가지(Logos 개발 서버, Codex)는 종료하지 않고 보고만 했다. 보헤님이 바로 선을 그었다.

> 로고스, 코덱스는 죽이면 안 된다. 다른 프로젝트는 죽이지 마라.
> 다른 프로젝트는 신경 쓰지 마.

이 정정은 AI의 영구 메모에 저장됐다. 이후로는 다른 프로젝트 프로그램은 번호와 시작 시각만 보고하고 건드리지 않는다.

**교훈**: "죽여라"처럼 되돌릴 수 없는 명령은 범위가 넓게 읽히기 쉽다. 대상을 번호나 이름으로 짚어 주면 안전하다.

**결과 (11-22 11시)**

8개 탭 완성. 도면 근거 품목 663개, AI가 상식으로 보완한 품목 347개. 문서와 검수 기록을 정리하고 공개 주소에 다시 올렸다.

### 6장. 보헤님이 공개 화면을 보고 개선점을 쏟아냈다 (11-22 12시)

보헤님이 공개 주소에서 직접 8개 탭을 본 뒤 **5가지를 한 번에** 말했다.

> 1. 절단 높이 기본값을 최대로. 2. 눈높이에서 마우스 조작감이 너무 이상하다(게임처럼 실제 사람이 고개를 들고 내려보는 각도 정도로 제한?). 3. 말투가 「도면에 적힌 치수다」 이런 식인데, 「값이다」도 「값」으로. 4. 탭을 누를 때 로딩 스피너가 있으면 좋겠다. 5. 고품질 렌더를 켜면 크롬 브라우저의 그래픽 가속 같은 게 있지 않나? **구현은 내가 하라고 하면 시작하고, 먼저 이해가면 설명.**

AI는 **코드를 열어 원인부터 확인**하고 항목마다 "지금은 이렇다 → 이렇게 바꾸자"를 표로 제안했다. 예를 들어 눈높이 조작이 이상한 까닭은 고개를 도는 방식이 아니라 "앞의 한 점을 중심으로 공전"하는 방식이어서 벽을 뚫고 천장으로 올라가기 때문이었다. 제안은 "제자리에서 고개 돌리기, 위아래 60도 제한, 높이 1.6m 고정"이었다.

**실수: "좋다"를 "시작"으로 읽었다**

보헤님이 "오케이 다 좋다. 다시 배포도 하면 된다. 그리고 UI 쪽 변경 논의하자. 지금 디자인이 전혀 없는데…"라고 하자, AI가 앞의 5건을 **구현 시작 신호로 읽고** 구현 일꾼을 띄웠다. 보헤님이 바로 멈췄다.

> 아직 구현하지 마. 준비되면 멈추고 논의하고 하자. 나머지도.

AI는 일꾼을 종료하고, 바뀐 파일이 없음을 확인했고, 이 규칙을 메모에 저장했다. 지금도 이 규칙이 유지된다.

**교훈**: 보헤님이 "내가 시작하라고 하면"이라고 했다면, 제안에 대한 "좋다"는 승인이 아니다. 보헤님 쪽에서는 "시작"이나 "구현해라"처럼 **분명한 단어**를 쓰고, AI 쪽에서는 애매하면 한 번 물어야 한다.

**디자인 논의**

보헤님이 윈도우 시계 앱의 어두운 화면 **스크린샷**을 보여 주며 "이런 컬러 테마로 가자"고 했다. AI는 스크린샷에서 색을 직접 뽑아 표로 정리하고 "이 색을 어디에 쓸지"를 제안했다. 범위는 A(색만)와 B(색과 모양)로 나눠 B를 추천했고, 보헤님이 "테마 B 3가지 제안대로"로 답했다.

이어서 보헤님은 "원본 도면을 누르면 버튼 안쪽이 색이 같아서 안 보인다"는 문제를 짚었고, 도면 썸네일에 마우스를 올렸을 때의 효과를 제안하라고 했다. 이어서 "근데 저거 자체가 클릭하면 보인다는 암시가 없다. 어떻게 하면 좋을까?"라고 했다. AI가 「크게 보기」 표시와 마우스 올림 효과 세트를 제안했고, 보헤님이 "그림 자체의 호버 효과는 없어도 될 것 같다. 그림이 살짝 커지는 건 오케이"라고 **일부를 조정**해서 확정했다.

마지막으로 보헤님은 이렇게 정리했다.

> 바로 구현하지 말고, 구현 계획 문서화해서 다음 세션에 하자. 세션 종료.

AI는 구현 대신 **계획 문서**를 남기고 세션을 끝냈다.

첫 배포 직후 보헤님이 "배포 끝나고 나면 URL 줘", 그리고 앞의 번호 답에서 "정리해"라고 했다. AI는 이 말들을 배포 지시로 읽고 **보헤님이 로컬에서 확인하기 전에** 한 번 더 배포했다. AI는 보고서에 이 사실을 숨기지 않고 적었고, 이전 배포본으로 되돌릴 수 있음도 함께 알렸다. 대화 기록에는 이에 대한 보헤님의 별도 정정이 없다.

**교훈**: 배포처럼 바깥에 영향이 큰 일은, 지시가 모호하면 AI가 되묻게 해 두는 편이 안전하다. AI가 스스로 보고했기 때문에 보헤님이 사실을 바로 알 수 있었다.

세션 종료: 문서 갱신, 개발용 프로그램 정리, 인수인계 문서 정리.

## 6. 보헤님의 지시 방식 — 효과가 컸던 10가지

1. **"제안해"로 시작한다.** 처음부터 만들라고 하면 AI가 방향을 짐작해서 만든다. 제안을 받아 보고 고르면 방향이 어긋나지 않는다.
2. **번호를 붙여 한꺼번에 답한다.** AI가 질문을 번호로 주면 "1. C. 2. 아니다. 3. 오케이."처럼 번호로 답한다. 왕복이 줄었다.
3. **"이해가면 설명"을 붙인다.** AI가 이해한 내용을 먼저 말하게 한다. 오해가 코드가 되기 전에 잡힌다.
4. **검증 규칙을 첫날 못박는다.** "독립 검증 에이전트로 만든 후 실제 도면과 같은지 검수해라"는 첫 대화에서 나왔고 끝까지 유지됐다.
5. **1개만 먼저 만든다.** 가장 작은 도면 1장을 먼저 끝내고 확인한 뒤 7장을 시켰다. 시험작에서 나온 규칙이 7장 전체에 적용됐다.
6. **판단을 맡길 곳은 분명히 맡긴다.** "높이는 없다. 네가 생각하는 상식적인 높이로 해라." AI는 이를 "다시 묻지 않는다"는 원칙으로 기록했고, 그 뒤 같은 질문을 반복하지 않았다.
7. **결정권은 내가 쥔다.** "구현은 내가 하라고 하면 시작", "배포는 내가 확인하고 하라고 하면". 시작과 배포는 항상 보헤님의 말이 있어야 했다.
8. **스크린샷으로 말한다.** 말로 설명하기 어려운 디자인은 참고 화면을 붙이거나 문제 화면을 붙여서 "이런 느낌으로", "여기가 구분이 안 간다"라고 했다.
9. **느낌 그대로 말하고 후보를 받는다.** "색이 좀 탁하다"라고만 해도 AI가 색 후보 4개와 근거를 비교 화면으로 보여 줬다. 보헤님은 고르기만 했다.
10. **세션을 끝낼 때 문서로 정리시킨다.** "문서화 다 하고, 세션 종료. 다음 세션에서 이어서 하자." 새 대화는 "업무준비" 한마디로 이어졌다.

## 7. AI가 틀린 일과 바로잡은 방법

| 실수 | 어떻게 드러났나 | 그 뒤 |
|---|---|---|
| 도구 장애로 저장 18번 거부 | AI가 직접 위험을 보고 | 대화 종료 후 이어받기로 복구. 제한 시간 연장 |
| 품질을 보헤님 PC 사양에 맞춰 낮춤 | 보헤님이 정정 | 품질 값은 일반 사양 PC 기준으로 정한다(영구 메모) |
| 「좋다」를 구현 시작으로 읽음 | 보헤님이 "아직 구현하지 마" | 명시적인 시작 지시가 올 때까지 논의만 한다(영구 메모) |
| 「고아 프로세스 죽여라」를 넓게 해석 | 보헤님이 정정 | 다른 프로젝트 프로그램은 보고만 한다(영구 메모) |
| 「톤을 맞춰라」를 회색 전체 변경으로 읽음 | 보헤님이 "배경색은 그대로" | 회색을 원래대로 돌렸다. 색이 한 곳에 모여 있어 되돌리기 쉬웠다 |
| 모호한 말을 배포 지시로 읽음 | AI가 스스로 보고 | 이전 배포본으로 되돌릴 수 있음을 알렸다 |

**AI의 보고를 그대로 믿지 않는 습관도 효과가 있었다.** 조율자 AI는 일꾼의 "다 했다" 보고를 받고도 직접 값을 읽고 화면을 열어 봤다. 그 과정에서 일꾼들이 놓친 결함을 찾았다(품목 선택 오류, 치수 라벨이 화면 밖으로 나옴, 라벨이 버튼을 덮음).

보헤님의 정정과 결정은 AI의 영구 메모에 규칙으로 저장돼 다음 대화에서도 유지됐다. 메모는 모두 7건이다: 독립 검증, 3D 방식 결정, 다른 프로젝트 프로그램 종료 금지, 품질 기준 PC, 시작 신호, 배포 시점, 화면 글자 명사형.

### 8.2 첫 요청 예시 (그대로 고쳐 쓸 수 있다)

> 폴더에 ○○ 파일이 있다. (무엇인지 한 줄). 이걸 (브라우저에서 보는 ○○)로 만들고 싶다. 어떤 방식으로 만들지, 어떤 기능을 넣을지, 화면 배치와 마우스 조작은 어떻게 할지 **제안해라.** 방식이 여러 개면 비교표로 보여주고 추천안을 말해라. **이해가면 설명.** 구현은 내가 시작하라고 하면 시작한다.

### 8.3 이어서 쓸 수 있는 문장

| 상황 | 문장 |
|---|---|
| 방향이 여러 개일 때 | 「각 안의 뜻, 차이, 근거를 표로 보여줘」 |
| AI가 이해한 내용을 확인하고 싶을 때 | 「이해가면 설명」 |
| 다 만든 뒤 | 「반드시 독립 검증 에이전트(만든 쪽과 다른 쪽)로 원본과 대조해라」 |
| 구현을 막고 싶을 때 | 「구현은 내가 하라고 하면 시작」 |
| 판단을 맡길 때 | 「네가 상식적으로 정해라. 다시 묻지 마라」 |
| 세션 끝낼 때 | 「문서화 다 하고 세션 종료」 |
| 새 세션 시작 | 「업무준비」 |
| 실수를 바로잡을 때 | 「(무엇)은 하지 마라」. AI는 이걸 메모에 저장한다 |

### 8.4 주의할 점

- **한 화면에서 같은 파일을 둘이 고치게 하지 않는다.** 일꾼을 나눌 때는 파일 범위를 나눈다.
- **AI의 "다 했다"를 그대로 받지 않는다.** 값이나 화면으로 한 번 확인하게 한다.
- **원본이 사진(스캔본)이면 정확도가 한계에 걸린다.** AI가 눈으로 읽고 옮기므로 검증을 반드시 둔다.
- **컴퓨터가 느리면 병렬 일꾼 수를 줄인다.** CPU가 가득 차면 일꾼들의 도구 호출이 시간 초과로 거부된다.
- **공개 배포는 결과물만 올린다.** 원본 자료와 작업 문서는 공개 저장소에 올리지 않았다.
